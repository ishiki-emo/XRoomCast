## 1. 空間共有 — 複数端末で同じ場所にアバターを固定する

現状、AR での設置は端末ごとに独立している(`ar.ts` のヒットテスト)。
同じ部屋にいる2人が同じ机にアバターを置いても、それぞれ別の場所に見える。
これを一致させると、会場に全員で同じアバターを囲む体験ができる。

必要なものは2つで、後者はほぼ揃っている。

- **A. 共有原点の確立** — 未着手。ここが本質的な難所
- **B. 原点相対のアバター配置を全員で共有** — Presence DO で視聴者位置を配れているので、
  `{position, quaternion, scale}` を1組足すだけで済む

### STYLY-NetSync は使わない

LBE 向けの Unity ネットワークモジュール
([styly-dev/STYLY-NetSync](https://github.com/styly-dev/STYLY-NetSync)、Apache-2.0)を候補として調べたが採らない。

- Unity パッケージ + Python サーバーで、トランスポートが ZeroMQ。**WebSocket 非対応でブラウザから接続できない**
- より本質的な問題として、**NetSync 自身は位置合わせの機構を持っていない**。
  全端末が既に同じ原点を共有している前提の設計で、同期しているのは Transform だけ。
  会場の設営で原点が決まっている、という運用でカバーしている
- XRoomCast は同期レイヤ(Cloudflare Realtime + Durable Objects)を既に持っているため、
  仮に WebSocket ブリッジを書いても得るものがない

借りる価値があるのは設計思想の方。
**physical transform と virtual transform の分離**と、
**Human Presence**(他人の実位置を表示して衝突を避ける)は、そのまま参考になる。

### 共有原点は2点手動キャリブレーションで作る

WebXR には自動で位置合わせをする現実的な手段がない。

| 方式 | 可否 |
|---|---|
| WebXR Marker Tracking | 廃止済み。使えない |
| Quest の Shared Spatial Anchors | ネイティブ SDK 限定。WebXR から触れない |
| VPS(Immersal 等) | 事前スキャンが要り、「URL を開くだけ」と相性が悪い |
| **2点手動キャリブレーション** | **採用** |

床に十字テープを2枚貼り、①=原点、②=+X方向をコントローラ先端(またはヒットテストのレティクル)で突く。

- 1点では向きが決まらないので**2点必要**。**2点目は1m以上離す**
  (先端が数cmずれても角度誤差が約1度に収まる)
- 高さは `local-floor` があっても端末ごとに床推定が数cmずれるため、**1点目のYをそのまま使う**
- 各端末が持つのは「自分の `local-floor` → 共有原点」の変換1個だけ。
  ネットワークには原点相対座標だけを流す(NetSync と同じ構造)
- **変換行列を `localStorage` に保存する**。HMD は実働2〜2.5時間でバッテリー交代=セッションが切れるため、
  これが無いと1日通しの運用が成立しない
- **原点に小さい仮想十字を常時表示する**。床のテープとの重なりで、スタッフが誰でもドリフトを判定できる
- 再キャリブレーションは10秒で終わる操作にしておく

#### 副次的な利点: 機種をまたげる

Meta の Shared Spatial Anchors と PICO の仕組みには互換性がなく、
**ネイティブアプリでは Quest と PICO を同じ空間に置けない**。

2点キャリブレーションは WebXR の `local-floor` から自前で変換を計算するだけなので、
ベンダーに一切依存しない。WebXR は右手系・Y-up・メートル単位で標準化されているため、
機種間の座標規約のズレもない。原始的な手法が、ネイティブの届かない範囲に届く。

### WebXR Anchors はドリフト対策であって位置合わせではない

`frame.createAnchor()` は ARCore / Meta のアンカー機構を WebXR から使えるようにしたもので、
SLAM の地図が更新されても貼った点が実物に追従する。
ただし**端末間で共有する仕組みが仕様に無い**ので、位置合わせの解にはならない。

順番は「手動で原点を決める → その位置に `createAnchor` → 以降そのアンカー空間に置く」。

永続化 `requestPersistentHandle()` は Quest Browser にはあるが、それだけに頼らず、
**素の2点キャリブレーション結果(位置と向き)も生の数値で保存**しておくこと。

### オクルージョンは事前スキャンメッシュが本命

描画機構は既にある(`ar.ts` の `planeOccluders`: `MeshBasicMaterial({colorWrite:false})` で深度だけ書き、
床は除外)。追加で要るのは「メッシュのロード」と「共有原点への位置合わせ」だけで、描画パスは再利用できる。

- **PICO 4 Ultra の実機プローブは mesh-detection ❌ / depth-sensing ❌**
  (plane-detection ✅ / anchors ✅)。端末からメッシュも深度も取れないため、
  Quest で有効な「`mesh-detection` の結果をそのまま使う」逃げ道が無く、事前スキャンが本命になる
- Quest は端末の深度で隠せるようになった(`depthOcclusion.ts`)。事前スキャンが要るのは PICO と、
  Quest でも深度センサーの届かない遠い物・粗い境界を詰めたいとき
- **オクルージョンを入れると位置合わせの精度要求が一段上がる**。
  アバターが3cmずれても誰も気づかないが、オクルージョンメッシュが3cmずれると全シルエット境界で破綻する。
  人間は輪郭の不一致に鋭敏
- 緩和策として**メッシュを法線方向に数cm内側へ縮める**。
  誤差が「隠しすぎ」でなく「隠し足りない」側に倒れる。
  何もない空中でアバターが欠けるのは一発で壊れて見えるが、柱に少しめり込むのは許容される
- 部屋メッシュは数MB出るので**会場ローカル配信専用**に切り分ける。
  遠隔視聴者に配る必要は無いし、会場の3D形状は機微な情報でもある

### iPad での体験撮影は共有原点の副産物

HMD で遊んでいる様子を iPad で外から撮るには、
**HMD の人が見ている物理的な位置に、iPad からもアバターが見える**必要がある。
これは共有原点そのものなので、iPad を「キャリブレーションに参加する端末の1台」として扱えば済む。

- iPadOS の Safari は `immersive-ar` 非対応なので、[EyeJack X](https://play.eyejack.xyz/) 経由で `ar.ts` を動かす
- 2点の指定は、コントローラの代わりに**画面中央のレティクル(ヒットテスト)**で床のテープを突く
- 撮影用に**DOMオーバーレイの UI を消す撮影モード**があるとよい(画面収録にそのまま使うため)
- 前後の重なりは期待しない。人がアバターの手前を横切ると、人の上にアバターが描かれる。
  アバターを人より奥に置く画作りで避ける
- 遅延は HMD 側と同じ(どちらも視聴者として同じバッファを経由する)ので、映像内で両者はずれない

着手前に iPad 実機で確かめること: EyeJack X 上で `localStorage` が残るか(キャリブレーション結果の保存)、
深度・画像マーカーが WebXR から使えるか(使えればテープを突く手間を省ける)。

### この層の位置づけ

共有原点・アンカー・オクルージョンは**すべてロケーションベース体験専用の上乗せ**で、
既存の配信設計を変えない。配信されているのはポーズデータなので、

- 遠隔視聴者 → 今まで通り、URL を開くだけ、数KB/s
- 会場にいる人 → 同じストリームに共有原点とオクルージョンを乗せる

同じ配信を両方が食べられる。

## 2. 追加オブジェクトの出し入れ

背景や小物を出せるようにする。配信者からアイテムを出せると演出の幅が広がる。

### 既存機構の一般化として作る

アバターの差し替えで通した経路がそのまま使える。

> R2 にアップ → `/api/vrm/*`(配信者キー必須) → Presence DO に状態を保存 →
> 全視聴者へ配布 → 途中入室者にも届く

これを「1個」から「N個のリスト」に広げる。配布の設計は実証済みで、増えるのは状態の持ち方だけ。

読み込みも追加依存が要らない。`avatar.ts` で既に `GLTFLoader` を使っているため、素の GLB はそのまま読める。

`compileAsync` + 工程ごとの `requestAnimationFrame` 分割、`detach()` と `dispose()` の分離といった
**フリーズ対策もそのまま効く**。むしろ `Avatar` から汎用ロード部分を切り出すのが正しい順序で、
オブジェクト機能はその副産物になる。

### 親フレームを最初に決める

ここが設計の分岐点。

| 親 | 挙動 | 用途 |
|---|---|---|
| `avatarRoot` 相対 | アバターと一緒に動く・縮む。卓上1/10でも整合 | 手に持たせるアイテム、足元の小物 |
| テーブル / 共有原点 相対 | 会場に固定され、全員で一致する | 盤面、カード、家具 |
| 視聴者ローカル | 各自の部屋に自由配置 | 装飾、視聴者ごとの演出 |

`avatarRoot` 相対は**今すぐ実装できる**。`PoseApplier` が配置フレーム対応済みで、
`AvatarScaleAdapter` のスケール追従もあるため。
テーブル相対は共有原点が前提なので §1 の後になる。

`AvatarScaleAdapter` を作ったときの知見(縮小すると揺れものが暴れる、アウトラインが太る)は
**オブジェクトでも同じ問題が出る**。あの仕組みを一般化して当てておく。

### 背景は AR と非 AR で別物

- **非 AR(PC・VR)** — `scenery.ts` の差し替え。全天球やステージセットを配れる
- **AR** — パススルーが本体なので背景を出せない(`scene.background = null` にしている理由)。
  出せるのは「置く」オブジェクトだけ

つまり**背景切り替えは非 AR 専用機能**として設計する。

### 配信者側の操作

`avatarConsole.ts` に足すのは素直だが、**HMD 配信中にも出したい**はず。
その場合は `xrPanelController.ts` の空間パネルにセクションを追加する。

ただしパネルは項目数が増えると使えなくなるため、
**よく使う数個をスロットに登録しておく**方式が現実的。全アセット一覧をヘッドセットから選ぶのは無理がある。

### 帯域

GLB は数MB出る。「数KB/s」はポーズ配信の話なので矛盾はしないが、オブジェクトが増えると累積する。

アバター切り替えと同じ「視聴者ごとに DL が終わった時点で出現」で当面は足りるはず。
演出として同時に出したい場合は、**先に配っておいて表示フラグだけを合図で同期する**二段構えが要る。
必要性は実際に使ってみないと判断できないので後回しでよい。

### 着手順

1. `avatarRoot` 相対のアイテム1個(共有原点を待たずに動く。`Avatar` からロード部分を切り出す)
2. 背景の差し替え(非 AR)
3. テーブル相対(§1 の後)

## 3. 想定しているユースケース

上の優先順位は、次のような体験を想定して決めている。

### 向いているもの

同室の HMD 複数台 + 遠隔視聴者で遊ぶ、**ターン制のテーブルゲーム**。

- **ターン制で低速**なので、`peers.ts` の 10Hz とネットワーク遅延に耐える
- **状態が離散的で小さい**。駒とカードは「どこに何がある」だけで、物理シミュレーションが要らない
- **駒はマスに吸着する**ので、指トラッキングが無いという最大の弱点が問題にならない
- **ルールの権威を Durable Object が持てる**。不正手を弾く、順番を管理する、状態を配る
- **共有原点が「卓」そのもの**になり、テーブルローカル座標が自然な単位になる
- 面白さの主役が盤面ではなく**人の表情と間**であり、アバター配信の強みと一致する

権利の面でも、トランプ・花札・囲碁将棋・人狼あたりは**ルール自体に権利が無い**ので実装しやすい。

向かないのは、反射神経を要するもの・細かい手指を使うもの・大量のオブジェクトを扱うもの。

### 情報の非対称は実装と一致する

伏せ札のあるゲームを作るなら、**Presence DO が視点ごとにフィルタして配る**必要がある
(全状態を配ると DevTools で相手の手札が読める)。これは**最初から設計に入れないと後から直せない**。

そして重要な点として、この制約は**見た目の演出とそのまま一致する**。
他人のカードは表面のデータがクライアントに届いていないので、描画すれば当然裏面にしかならない。
「自分以外には両面が裏に見えるカード」は、正しく情報を絞った結果そのものであり、
チートが原理的に不可能な状態が画になっている。

現実のトランプは「裏面を相手に向ける」物理制約でこれを実現しているため、
扇状に持つ・角度を気にする・覗き見に警戒する労力が要る。
同室 AR ではヘッドセットの中は覗けなくても**手の動きと視線は丸見え**なので、
この方式でないとそもそも成立しない。

### 観戦モードは逆転する

視点別フィルタを1回書けば、3段階に使える。

| | 見えるもの |
|---|---|
| プレイヤー | 自分の手札だけ |
| 遠隔視聴者 | 全員の手札 |
| 配信者コンソール | 全部 + 誰が何を見ているか |

`config.ts` のロール型(viewer / studio)と、
Presence WS 接続時に Worker が配信者キーを検証して DO の attachment へ渡す仕組みが既にあるため、
土台は完成している。増えるのは「何を配るか」の判断だけ。

ポーカー中継のホールカードカメラと同じ構造で、
**手札が見えるからこそプレイヤーの読み違いが面白くなる**。

ただし**同室の観客はプレイヤーに声が届く**。ここが唯一の漏洩経路になる。
XRoomCast は遠隔視聴者と同室プレイヤーを最初から分けているので、

- 遠隔視聴者 → 声が物理的に届かない。リアルタイムで全部見せて安全
- 同室の観客 → 見せないか、プレイヤーと同じ情報量に落とす

という扱いになる。会場にいる人ほど情報が少ない、という普通とは逆の構造になる。

コメント機能も同様で、`spatialChat.ts` を**プレイヤーには出さない**
(配信者と遠隔視聴者だけ)。でないと視聴者が実況で漏らす。
