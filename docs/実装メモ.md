# 実装メモ

XRoomCast の実装の詳細と、そうしている理由の記録です。
機能ごとの仕組み・注意点・ハマりどころをまとめています。

- 動かすまでの手順は [../SETUP.md](../SETUP.md)
- 概要は [../README.md](../README.md)

「Phase 0〜2c」は初期の開発段階の呼び名です。現在の実装はそこから大きく先行しており、
マルチルーム・アバターの切り替え・HMD配信などは後半の節にまとめています。

> ソースコードのコメントにある `§6` `§7` などの節番号は、初期設計時の仕様書を指しています。
> その仕様書はリポジトリに含めていません(現在の実装と乖離しているため)。
> 各仕組みの現状は、このファイルに書いてあるものが正です。

## パッケージ構成

「アバター同期と音声配信のコアはそのまま使い、UIと認証は載せる側が用意する」
という形を成り立たせるため、アプリ固有の配線とコアを分けてある。

| | 中身 | 依存 |
|---|---|---|
| `packages/protocol` | ポーズのバイナリ形式 | **なし** |
| `packages/sync` | トランスポート抽象と実装(WS / Cloudflare SFU)、ジッタバッファ、資格情報の抽象、ルーム名の規則 | **なし**(protocolのみ) |
| `packages/viewer-core` | VRMの読み込みとポーズ適用、待機モーション、視聴者の気配、空間オーディオ、舞台 | three, three-vrm |
| `apps/viewer` | 画面のUI、AR/MR、配信者コンソール、URLクエリの解釈 | 上記すべて |
| `apps/viewer/worker` | サーバー側(ルーム・状態・秘密の保管・認可) | なし |
| `apps/bridge` | VMC(VSeeFace等)からの配信中継。**HMD配信では不要** | node系 |

要点が3つある。

- **Cloudflareは前提ではない。** 同期の抽象は
  [transport.ts](../packages/sync/src/transport.ts) のわずか十数行で、Cloudflare SFU は
  その1実装にすぎない(もう1つ `WebSocketTransport` が実在して動いている)。
  自前のサーバーで回したい場合は `Transport` を実装すればコアはそのまま動く
- **`sync` は three に依存しない。** 唯一の依存だったクォータニオン補間を
  [quaternion.ts](../packages/sync/src/quaternion.ts) へ自前で持ち直した
  (three の実装との一致は test/quaternion.test.ts で突き合わせている)。
  これにより、描画エンジンの違う別クライアントからも同期層をそのまま使える
- **`viewer-core` はDOM要素に触らない。** 画面のUI・AR/MR・配信者コンソールは
  すべて `apps/viewer` 側にあるので、任意のUIの下に組み込める

`three` と `@pixiv/three-vrm` は `viewer-core` の **peerDependencies** にしてある。
依存として抱えると利用側と別インスタンスになり、`instanceof` が静かに false になって
何も描画されない、という事故が起きるため。

## セットアップ

```sh
npm install
```

VRMファイルをリポジトリにはコミットしないため、各自で用意して
`apps/viewer/public/avatar.vrm` として配置する(`fixtures/README.md` 参照)。

## Phase 0: 静的VRM表示

```sh
npm run dev
```

ターミナルに表示されたURL(既定は http://localhost:5173 。使用中なら自動で別ポートになる)を
ブラウザで開くと、`apps/viewer/public/avatar.vrm` がTポーズで表示される。マウスドラッグで回転、ホイールでズーム、右ドラッグでパン。

## Phase 1: 動的VRMロード

VRMを実行時にロードできる。

- **URLクエリ**: `http://localhost:5173/?vrm=<URLエンコードしたVRMのURL>`
- **画面上のUI**: 左上の入力欄にURLを入れて「ロード」(Enterでも可)

ロード中はバイト数ベースのプログレスを表示し、失敗時(404 / CORSエラー / 非VRMファイル)は
エラーメッセージを表示して直前のモデルの表示を維持する。差し替え時は旧モデルを
`VRMUtils.deepDispose` で破棄するため、繰り返し差し替えてもメモリは増加しない。

別オリジンからロードする場合の注意:

- 配信元がCORSを許可している必要がある。ローカルで試す場合の例:
  `npx http-server apps/viewer/public -p 8081 --cors`
  → `http://localhost:8081/<VRMのファイル名>` を入力欄に指定
- **Cloudflare R2で配信する場合は、バケットにCORSルール(`GET` メソッド、対象Origin)の
  設定が必要**。設定がないとブラウザがフェッチをブロックする。

将来のDL抑制(署名付きURL+暗号化配信)を見据えて、ローダーの入口
(`loadVRM`)はURLと `ArrayBuffer` の両方を受け付ける。

## Phase 2a: ダミーモーション適用(通信なし)

- `packages/protocol` — パケット仕様(仕様書§6)のエンコード/デコード共有ライブラリ。
  `npm test` でラウンドトリップ単体テストを実行。
- `fixtures` — ダミーモーション生成器(サイン波で「両手を振りながら頭が揺れる」30Hz)。
  `npm run generate:motion` で `fixtures/dummy-motion.bin`(§6形式・タイムスタンプ付き)を
  生成・デコード検証する。ペイロードは約3KB/s。
- ビューアの「デモ再生」ボタンでダミーストリームを実時間再生する。パケットは実経路と
  同じくエンコード→デコードを通り、以下のパイプラインでアバターへ適用される:
  1. ジッタバッファ(目標遅延100ms、位置lerp・回転slerp)
  2. 頭回転の適用+頭位置差分によるhipsルートモーション
  3. 足の接地固定IK(レスト時の足首位置に2ボーンIKで固定。ルートモーションは膝で
     吸収するため足が滑らない。hipsがレストより高く上がった場合のみ足が浮く)
  4. 手首目標への2ボーンIK(自前実装、肘ポールは体側やや後方・下方)
  5. 表情(辞書パケットで表情ID→名前を解決、未受信IDは無視)
  6. 指カール値の3関節展開+スプレッド
- 「パケット10%ドロップ」チェックで欠落シミュレーションができる(補間で破綻しないことの確認用)。

実装メモ: `VRMUtils.rotateVRM0` はVRM 0.xの `vrm.scene` をY軸180°回転させるため、
正規化ボーンのローカル系とワールド系が0.xと1.0で一致しない。ワールド系の値を
ローカルへ持ち込む箇所は必ずリグのワールド回転(`PoseApplier` の `rootQuat`)で
変換すること(怠るとルートモーションが毎フレーム発散する)。

## Phase 2b: VMC実経路(ローカルWebSocket)

VSeeFace → ブリッジ → ブラウザの実経路。

```sh
# ターミナル1: ブリッジ(VMC受信→§6シリアライズ→WS配信)
npm run bridge     # 既定: VMC_PORT=39539, WS_PORT=8080(環境変数で変更可)

# ターミナル2: ビューア
npm run dev
```

ブラウザで左上の「ws://localhost:8080」欄の **接続** を押すと追従が始まる。

### VSeeFace側の設定

1. VSeeFaceでアバターを選び、Webcamトラッキングを開始する
2. **設定(General settings)→「OSC/VMC protocol」の送信(Send data with OSC/VMC protocol)を有効化**
3. 送信先: IP `127.0.0.1`(ブリッジが別マシンならそのIP)、**ポート `39539`**
4. ブリッジのコンソールに毎秒 `[stats] 受信 ... msg/s` が出れば受信できている

### VSeeFaceなしで動作確認する場合

VMCシミュレータ(両手振り+頭揺れ+表情+指の開閉を60Hzで送信)を同梱している:

```sh
npm run sim                                        # 手振りモード
npm run sim --workspace apps/bridge -- right       # 右手だけ挙げる(§7鏡像確認用)
```

### 実装のポイント

- VMCの `/VMC/Ext/Bone/Pos` は**親ボーン相対のローカル姿勢**で届くため、ブリッジで
  HipsからFK合成してHead/両手首のルート空間姿勢を求めてから§7変換して送出する
- ボーン状態は `/VMC/Ext/T`(フレーム区切り)で一括反映する(複数UDPパケットに
  分かれて届くボーン群を受信途中でFK合成すると、新旧フレーム混成の破綻ポーズになる)
- 1tickで0.4m以上跳ぶ位置はスパイクフィルタで抑制(3tick継続で本物として受理)。
  トラッキングの一瞬の誤検出がそのまま中継されるのを防ぐ
- **複数のVMC送信元**(例: VSeeFaceとシミュレータの同時送信)を検出すると警告ログを
  出す。混線するとポーズが交互に上書きされて暴れるので、必ずどちらかを止めること
- 表情名はVRM 0.x名(Joy等)をVRM 1.0名(happy等)へブリッジで正規化する
- 送信レートはポーズ30Hz/表情・手指15Hz。WindowsのsetIntervalは分解能が粗い
  (約15.6ms)ため、絶対時刻基準のスケジューリングで30Hzを維持している
- ビューアは切断時に指数バックオフ(0.5s→最大8s)で自動再接続する。ブリッジ再起動で
  タイムスタンプが不連続になった場合はジッタバッファを仕切り直して再生を続行する
- トランスポートは `Transport` インターフェース([packages/sync/src/transport.ts](../packages/sync/src/transport.ts))で
  抽象化済み。Phase 2cでSFU実装に差し替える

## Phase 2c: Cloudflare Realtime SFU

WebSocketの代わりにCloudflare Realtime SFUのDataChannel(一方向:
publisher→subscribers)で配信する。別ネットワークのマシン・スマホや
複数ブラウザからの同時視聴が可能になる。

### セットアップ

1. [Cloudflareダッシュボード](https://dash.cloudflare.com/) → Realtime → Create App
2. リポジトリルートに `.env` を作成(`.env.example` 参照):

```
CF_REALTIME_APP_ID=<App ID>
CF_REALTIME_APP_SECRET=<App Secret>
```

**App Secretはブリッジ(Node)だけが読む。** ビューアのセッション作成は
ブリッジのプロキシAPI(`/api/sfu/*`)経由で行うため、Secretがブラウザへ
渡ることはない。

### 使い方

`npm run bridge` 起動時に `.env` があればブリッジがパブリッシャーセッションを
自動確立する(ログに `[sfu] パブリッシャー接続完了` が出る)。ビューア左上の
セレクタで **SFU** を選び、接続先にブリッジのHTTP URL(既定
`http://localhost:8080`)を入れて接続する。WebSocketとSFUはセレクタで
いつでも切り替えられる(受け入れ条件のフラグ)。

別マシン・スマホから視聴する場合:

```sh
npm run dev -- -- --host   # ビューアをLANに公開
```

スマホのブラウザで `http://<PCのIP>:5173` を開き、SFUの接続先に
`http://<PCのIP>:8080` を指定する(ポーズデータ自体はCloudflare経由なので、
ブリッジAPIに届きさえすればよい)。

### 実装のポイント

- 手順は公式 `cloudflare/realtime-examples` の echo-datachannels に準拠
  (sessions/new でSDP交換 → datachannels/new で negotiated ID取得 →
  `createDataChannel(name, { negotiated: true, id })`)
- ブリッジ側のWebRTCは `node-datachannel` のWebRTCポリフィルを使用
- 辞書と表情全量は5秒間隔で定期再送する(§6.5。SFUは一方向で
  途中参加者に接続時送信ができないため)

## ビューアの公開(Cloudflare Workers 静的アセット)

Cloudflareの設定ファイルは**アカウント固有のIDを含むためコミットしていない**。
テンプレートをコピーして自分の値を入れる。

```sh
cd apps/viewer
cp wrangler.example.jsonc wrangler.jsonc
npx wrangler kv namespace create SFU_STATE   # 出力されたIDを wrangler.jsonc の <KVネームスペースのID> に貼る
```

```sh
npx wrangler login        # 初回のみ(+ workers.devサブドメインの登録が必要)
npm run deploy:viewer     # ビルド → distからVRM除去 → デプロイ
```

公開URL: `https://<Worker名>.<workers.devサブドメイン>.workers.dev`
(初回デプロイ時にwranglerが実際のURLを表示する)

- **VRMファイルはデプロイに含めない**(ライセンス・DL抑制の方針+25MB上限)。
  公開ページでは `?vrm=<CORS許可済みURL>` か入力欄でVRMを指定する
- **SFUプロキシはWorker自身が持つ**(`/api/sfu/*`)ため、公開視聴に
  トンネルは不要。ブリッジはSFU接続時に自分のセッションIDをWorkerへ登録し
  (`BRIDGE_TOKEN` によるBearer認証+5分ハートビート)、WorkerがKV経由で
  サブスクライバーへ案内する。必要なWorker secret:

```sh
npx wrangler secret put CF_REALTIME_APP_ID     # Realtime App ID
npx wrangler secret put CF_REALTIME_APP_SECRET # Realtime App Secret
npx wrangler secret put BRIDGE_TOKEN           # ブリッジ登録用(ランダム文字列)
```

ブリッジ側の `.env` にも `BRIDGE_TOKEN=<同じ値>` と
`VIEWER_ORIGIN=https://<デプロイ先のURL>` を書く。
KVネームスペース(`SFU_STATE`)の作成とIDの設定は上記のセットアップ手順を参照。

`cloudflared tunnel --url http://localhost:8080` によるブリッジの直接公開は
Worker登録を使わない場合の代替手段として残る(WS視聴をインターネットへ
出したい場合もこちら)。

カスタムドメイン(例: stream.example.com)を使う場合は、ドメインのDNSを
Cloudflareへ移管したうえで `apps/viewer/wrangler.jsonc` に
`"routes": [{ "pattern": "stream.example.com", "custom_domain": true }]`
を追加して再デプロイする。

### VRMのR2ホスティング(トークン付き同一オリジン配信)

公開ページで使うVRMは**R2の非公開バケット**に置き、ビューアWorker自身が
`/vrm/<キー>?k=<トークン>` で配信する(`apps/viewer/worker/index.ts`)。
バケットは非公開のまま・同一オリジンなのでCORS不要・URLは恒久。

```sh
npx wrangler r2 bucket create <バケット名>                          # 初回のみ
npx wrangler r2 object put <バケット名>/avatar.vrm --file <VRMのパス> --remote
npx wrangler secret put VRM_TOKEN                                # 配信トークン(照合用)
```

- トークン不一致・未指定は403。トークンをローテートすれば出回ったリンクは無効化できる
- ワンリンク共有の組み立て(**固定リンク**。`<>`を実値に置換):

```
https://<デプロイ先のURL>/?vrm=<urlencode(/vrm/avatar.vrm?k=トークン)>&transport=sfu
```

SFUプロキシが同一オリジンにあるため `server=` は不要。配信の手順は
「VSeeFace起動 → `npm run bridge`」だけで、リンクは毎回同じものが使える。

### アバターのアップロードと配信中の切り替え

配信者コンソール(`/broadcast/...`)からVRMをアップロードし、「切り替え」を
押すと**視聴中の全員がそのVRMを読み込み直す**。R2のキーはルームごとに
`rooms/<ルーム>/<ファイル名>` へ分かれる。

- `POST /api/vrm/upload?room=&name=` : R2へアップロード(ボディがVRM本体)
- `GET  /api/vrm/list?room=`         : そのルームのVRM一覧
- `POST /api/vrm/delete?room=&name=` : 削除
- `GET  /api/avatar?room=`           : 現在のアバター
- `POST /api/avatar?room=`           : 切り替え(全視聴者へ同期)

すべて配信者キー(BROADCAST_KEY またはルームの配信トークン)が必要。

切り替えは Presence Durable Object 経由で配られ、**現在のアバターはDOに
保存される**ため、あとから入室した視聴者も同じアバターで表示される。

視聴側の挙動:

- 各視聴者は通知を受け取った時点でダウンロードを始める。完了するまでは
  **それまでのアバターを表示し続ける**ので、切り替えの瞬間に何も居なくなる
  ことはない(切り替わるタイミングは視聴者ごとにばらつく)
- まだ何も表示できていない初回ロード中は、**クリスタルの仮アバター**
  (`packages/viewer-core/src/placeholderAvatar.ts`。プリミティブのみで外部ファイル不要)を立てる
- ロードに失敗した場合は元のアバターを維持する

制約と注意:

- アップロードの上限は80MB(Workersのリクエストボディ上限100MBの手前で弾く)。
  視聴者は切り替えのたびにこのサイズをダウンロードするため、
  **イベントで使うVRMは軽いほどよい**
- ファイル名は日本語も使えるが、パス区切り・相対参照・制御文字は拒否される
- 切り替え先に指定できるのは**自ルームにアップロードしたVRMか既定VRM**のみ
- R2に残り続けるので、イベント後は配信者コンソールから削除する

### 視聴用の短縮URL(/watch/<キー>)

長いパラメータ付きURLの代わりに、`/watch/<WATCH_KEY>` を開くだけで
視聴パラメータ(既定VRM+トークン+SFU自動接続)へリダイレクトされる。
組み立てはWorkerが行うため、共有するのは短いURL1つでよい。

```sh
npx wrangler secret put WATCH_KEY   # 視聴キー(ランダム文字列)
```

- 既定VRMは `wrangler.jsonc` の `vars.DEFAULT_VRM_KEY`(R2のキー名)で変更
- キー不一致は404。WATCH_KEYをローテートすれば出回った視聴URLだけを
  無効化できる(VRM_TOKENとは独立)
- この形式は**既定ルーム(`main`)専用**。複数のルームを使い分ける場合は次節へ

### ルーム(同時に複数の配信を成立させる)

SFUのパブリッシャー・同接・コメントはすべて**ルームごとに分かれる**。
ルームは `?room=<名前>` で指定し、未指定なら `main`(ルーム導入前と同じ
Durable Objectインスタンスを引き継ぐので、既存の配信URLはそのまま動く)。

ルーム一覧はサーバーに保存せず、**マスターシークレットからHMACで
トークンを導出する**。これによりルームをいくつ作っても状態管理が要らず、
ルームごとに異なる鍵を配れる。

```sh
npx wrangler secret put ROOM_SECRET   # ルームトークン導出用(ランダム文字列)
```

同じ値をリポジトリルートの `.env` にも書き、URLを生成する:

```sh
npm run room -- event-2026 https://<デプロイ先のURL>
# 視聴URL   : .../watch/event-2026/<22文字のトークン>
# 配信者URL : .../broadcast/event-2026/<22文字のトークン>
```

- ルーム名は英数字・ハイフン・アンダースコアの1〜64文字
  (Durable Objectの名前とKVキーになるため文字種を制限している)
- 視聴トークンと配信トークンは用途ごとに別導出。視聴URLが漏れても
  マイク配信やトラック公開はできない
- `BROADCAST_KEY` は全ルームに通用する**マスターキー**として残る
- ブリッジは配信するルームを `.env` の `ROOM=` で指定する
  (視聴URLのルームと一致していないとパブリッシャーが見つからない)
- ルームを無効化したいときは `ROOM_SECRET` をローテートする
  (全ルームのURLが一斉に無効になる点に注意)

### 認証・認可の差し替え点

このソフトは「URLを知っている人＝権限がある人」というケーパビリティ方式で、
利用者という概念を持たない。**アバター同期と音声配信のコアはそのまま使い、
認証は載せる側が用意する**という形を成り立たせるため、差し替え点を
サーバー・クライアントに1つずつ置いてある。

| | 場所 | 役割 |
|---|---|---|
| サーバー | [worker/auth.ts](../apps/viewer/worker/auth.ts) の `authorize()` | 誰が何をしてよいかの判定 |
| クライアント | [src/auth.ts](../apps/viewer/src/auth.ts) の `createAuth()` | 資格情報をどこから取り、どう載せるか |

コア(`sfuTransport` / `poseStream` / `poseApplier` / `peers` / `spatialAudio` /
`@xroomcast/protocol`)は認証を一切知らない。上の2つ以外に秘密を触る場所は無い。

#### サーバー: authorize()

```ts
authorize(env, request, url, { scope, room }): Promise<{ ok: boolean; userId?: string }>
```

`scope` は `viewer` / `broadcaster` / `publisher` / `vrm` の4種。
ルーティングやSFUの中継(`worker/index.ts`)には**秘密の比較が一切残っていない**ので、
この関数を書き換えればCookie検証でもIdPのJWT検証でも載せられる。

- **視聴の認可は長らく判定点そのものが無かった。** `/watch/<キー>` はURLを
  組み立ててリダイレクトするだけで、その先の `/api/presence` とSFUのAPIは
  `?room=` を見るだけだったため、**ルーム名(既定は `main`)を知っていれば
  鍵なしで視聴できてしまう**状態だった。匿名で気軽に見られること自体は
  狙いどおりだが、「見せない」を選べないのは設計の穴だった
- 既定(`vars.REQUIRE_VIEWER_TOKEN` 未設定)の `viewer` は**常に許可**。
  従来どおりの匿名視聴で、挙動は変わらない
- `"1"` にすると `WATCH_KEY` または `HMAC(ROOM_SECRET, "watch:<ルーム>")` を要求する。
  この視聴トークンは `/watch/...` のリダイレクト時に `?wt=` としてビューアへ引き継がれる
- `viewer` の呼び出し元は `/api/presence` と、視聴側が触るSFUエンドポイント全部。
  **presenceだけ塞いでもSFUが空いていればモーションと音声は取れてしまう**ため、
  パブリッシャー登録系(別scopeで認可)を除いた `handleSfuApi` の入口でまとめて通す
- `userId` は独自認証を入れたときの受け口。返すと `/api/presence` が検証済みの値として
  Presence Durable Objectの接続attachmentまで運ぶので、コメントや視聴ログを
  アカウントに紐づけられる。既定の鍵方式では常に `undefined`

#### クライアント: createAuth()

```ts
interface AuthProvider {
  headers(): Promise<Record<string, string>>;  // fetch / XHR 用
  query(): string;                             // WebSocket / sendBeacon 用
}
```

以前は `Authorization: Bearer ${key}` が5つのモジュールに直書きで、出所も各々が
`?key=` を読んでいたため、認証方式を変えるには全部を書き換える必要があった。
いまは各モジュールが `AuthProvider` を受け取るだけになっている。

- `headers()` を**非同期にしてある**のは、トークンのリフレッシュを挟めるようにするため
- `query()` が別にあるのは、**ブラウザのWebSocketと `sendBeacon` はヘッダを
  付けられない**ため。presenceの接続とタブを閉じる際の登録解除がこれに当たる
- VRMのアップロードだけはXHR(上りの進捗を取りたい)なので、ヘッダを
  同期的に積む必要がある。`open()` の前に `await headers()` してから渡している

### 視聴ページ(?watch=1)と同接カウント

`/watch/<キー>` 経由はタイトル+説明つきの視聴専用レイアウト
(16:9ステージ、操作UI非表示)になり、ステージ下に受信統計
(KB/s・pkt/s・累計・fps)と**同時視聴者数**を表示する。

ポーズパケットが5秒途絶えると「⏸ 配信は停止中です」オーバーレイを表示し、
再開すると自動で消える。対になる挙動として、**ブリッジはトラッキング元
(VSeeFace)からのボーン受信が2秒途絶えたら送信を止める**(止めないと
最後のポーズを送り続けてしまい、視聴側で停止を検知できない)。

### 待機モーション(クライアント側生成)

配信が届いていない間(接続前・停止中)は、**ビューア側だけで生成した待機
モーション**を再生する(`packages/viewer-core/src/idleMotion.ts`)。サーバーからは何も送られない。

- 呼吸・体重移動・ゆっくりした見回し・まばたきを、周期の違うサイン波の
  合成で作る(時刻の純関数。同じ時刻なら常に同じ姿勢)
- 出力は受信ストリームと同じ `SampledFrame` なので、PoseApplierのIK・
  足接地・AR設置/卓上スケールへの追従がそのまま効く
- 基準位置はモデルごとのレスト姿勢(`Avatar.restPose`)から測る。頭の高さと
  腕の長さから「腕を下ろした自然な姿勢」を求めるので、身長や体型が違っても
  沈んだり腕が伸びきったりしない
- パケットが届くと0.7秒かけて配信側へクロスフェードし、5秒途絶えると
  待機モーションへ戻る(デモ再生中は常に配信側扱い)

同接はWorkerの**Durable Object(`Presence`)**が数える。視聴ページが
`/api/presence?room=<ルーム>` へWebSocket接続し、DOが開いているソケット数を
増減のたびに全員へブロードキャストする(ハイバネーションAPI使用でアイドル
コストほぼゼロ)。DOはルームごとに1インスタンスなので、同接もコメントも
ルーム間で混ざらない。

### 音声配信(配信者コンソール)

`/broadcast/<BROADCAST_KEY>`(既定ルーム)または
`/broadcast/<ルーム>/<トークン>` を開き「マイク配信を開始」を押すと、マイクが
Opus音声トラックとしてSFUへパブリッシュされ、同じルームの視聴ページで
再生できる(ページを開いている間だけ配信)。

```sh
npx wrangler secret put BROADCAST_KEY   # 配信者キー(ランダム文字列)
```

- 手順は cloudflare/calls-examples の echo に準拠(空セッション作成 →
  `tracks/new` でSDP交換・トラック公開。購読側は同じPeerConnectionへ
  `tracks/new`(remote)+ renegotiate で追加)
- 音声セッションIDはKVで共有(ポーズのパブリッシャー登録と同じ方式。
  4分ハートビート+ページ閉鎖時はsendBeaconで解除)
- トラックの公開(location: local)はBROADCAST_KEY必須。視聴(remote)は不要
- 視聴ページは音声トラックを受信するとステージ右上に「🔇 タップで音声ON」を
  表示する(ブラウザの自動再生制限のため、ミュート解除には操作が必要)
- 帯域は音声約6〜8KB/s/人(Opus)。ポーズと合わせても動画の1/100以下

### 匿名コメント

同じWebSocket(Presence DO)でコメントも送受信する。

- 送信: ステージ下の入力欄(匿名・アカウントなし)。200文字まで、
  ソケット単位で1秒1回のレート制限
- 表示: ステージ左下のオーバーレイに積み上がる(最新10件、textContentで
  挿入するためHTMLは無害化される)
- 直近50件をDOストレージに保存し、途中参加者にも履歴を表示する

- これは「カジュアルなDL防止」であって完全防止ではない(視聴できる人は
  原理的に取得もできる)。本気の抑制は署名付き期限トークン+メモリ上復号
  (Phase 3以降)で強化する
- ブリッジの `/vrm/` ルート(トンネル経由配信)はLAN・開発用として残してある
