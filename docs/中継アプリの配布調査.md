# 中継アプリの配布調査 — 「ダウンロードして起動するだけ」にできるか

PCで VSeeFace などの VMC プロトコル(UDP/OSC)を使って配信するときに必要な中継プログラム
(`apps/bridge`)を、配信者が Node.js などを入れずに使える**ビルド済みの実行ファイル**
(できればタスクトレイ常駐アプリ)として配る方法を調べた記録。段階0(配信者URLだけで動く)と段階1(SEA の exe)は実装した(docs/実装メモ.md の「PC配信の中継アプリを配る」)。配信者ごとのURL(§4 案1)と段階2(Electron)はまだ。

結論を先に書く:

- **できる。** Node.js の Single Executable Applications(SEA)で、いまの `apps/bridge` を
  ほぼそのまま1つの `.exe` にでき、手元の Windows で起動・VMC受信・配信まで動いた(§5)
- ただし**配る前に必ず直すべき点が1つある**。いまの中継プログラムは Cloudflare Realtime の
  **App Secret をPCに置いて**SFUを直接叩いている。配信者に配る実行ファイルにこれを持たせると、
  配信者の数だけ App Secret が出回る。Worker にはすでに配信者キーで使える SFU の中継 API が
  あるので、中継プログラムをそちらへ切り替え、**設定は「配信者URLを貼るだけ」**にする(§4)
- いまの配信者キーは**ルーム単位**で、同じルームの配信者どうしは区別できない(1人だけの取り消しも
  できない)。配る前提なら、配信者URLを**配信者ごとに発行**する形にしておくとよい(§4)
- タスクトレイ常駐と設定画面まで作るなら **Electron** が無理がない。SEA だけではトレイを
  作れない(§3)
- 推奨は**2段階**: まず SEA で「ダブルクリックで動く exe」を出し(数日)、続けて Electron の
  トレイアプリに載せ替える(1〜2週間)。どちらも GitHub Actions + GitHub Releases で配る(§6, §7)

## 1. いまの中継プログラムの作り

### 起動のしかた

| 経路 | 中身 |
|---|---|
| `配信開始.bat` | `.env` と `node` の有無を確かめ、`npm run bridge` を実行する |
| `npm run bridge` | `apps/bridge` の `dev` スクリプト = `tsx src/index.ts`(TypeScript をその場で実行) |
| `セットアップ.bat` | Node.js が無ければダウンロードページを開く → `npm install` → `node apps/setup/server.mjs` |

つまり配信者のPCには **Node.js 本体 + リポジトリ一式 + `npm install` 済みの `node_modules`**
が要る。`tsx`(開発用の依存)で TypeScript を直接動かしているので、ビルド工程も無い。

### 依存パッケージ

| パッケージ | 役割 | ネイティブ? |
|---|---|---|
| `node-datachannel` 0.32 | WebRTC(DataChannel)で Cloudflare Realtime SFU に配信する。`node-datachannel/polyfill` の `RTCPeerConnection` を使用 | **あり**。`build/Release/node_datachannel.node`(Windows x64 で約7.2MB、N-API 8)。インストール時に prebuild を取得 |
| `osc-min` | VMC(OSC)のパース | なし(古い `Buffer()` を使うため実行時に非推奨警告が出る) |
| `ws` | ローカルの WebSocket 配信(SFU を使わない場合・開発用) | なし(`bufferutil` 等は任意依存) |
| `@xroomcast/protocol` | パケットのエンコード。ワークスペース内の TS ソースを直接 import | なし |

**単一実行ファイル化で問題になるのは `node-datachannel` のネイティブアドオンだけ**。
これは `.node`(DLL)なので、実行ファイルの中からそのまま読み込めず、一度ディスクに書き出して
`process.dlopen()` する必要がある(どのツールでも事情は同じ)。

### 設定の読み方(`.env`)

`apps/bridge/src/index.ts` の冒頭で `process.loadEnvFile()` を使い、**ソースの位置から相対で**
リポジトリ直下の `.env` を読む(`new URL('../../../.env', import.meta.url)`)。読むキー:

| キー | 用途 | 配布時の扱い |
|---|---|---|
| `CF_REALTIME_APP_ID` / `CF_REALTIME_APP_SECRET` | SFU の REST API を直接叩く | **配信者に渡してはいけない**(§4) |
| `VIEWER_ORIGIN` | Worker の URL。パブリッシャー登録に使う | 配信者URLから取れる |
| `BRIDGE_TOKEN` | パブリッシャー登録の認証(全ルーム共通) | 配信者キーで代替できる(Worker 側で実装済み) |
| `ROOM` | 配信するルーム | 配信者URLから取れる |
| `PUBLISHER_ID` | 複数配信者のときの席の識別 | 設定画面で自動生成して保存すればよい |
| `VMC_PORT` / `WS_PORT` | 受信ポート(既定 39539 / 8080) | 詳細設定 |
| `ROOM_SECRET` | ウィザードが書くが、中継プログラムは**読んでいない** | 不要 |

加えて `VRM_DIR`(`apps/viewer/public`)をソース相対で決めて `/vrm/` で配っている。
トンネル経由の旧方式の名残で、R2 配信になった今の構成では配布版には要らない。

### セットアップウィザード(`apps/setup`)との関係

ウィザードは**運営者(=Cloudflare アカウントの持ち主)向け**の道具で、`wrangler` で KV・R2・
Worker を作ってデプロイし、シークレットを登録したうえで、**最後のついでに**中継プログラム用の
`.env` を書き出している(`steps.mjs` の手順8)。

いまは「運営者=配信者=同じPC」を前提にしているのでこれで回るが、管理画面からルームを開設して
**配信者URLを別の人に渡す**運用(直近のコミット)では、配信者は Cloudflare にもウィザードにも
触れない。配布版の中継アプリは**ウィザードから切り離し、配信者URLだけで動く**ようにするのが筋。

|---|---|---|---|---|---|---|---|
| **Node.js SEA**(+ esbuild で1ファイル化) | ◎ | ○(署名の付け直しが要る) | **exe 約91MB / zip 約35MB**(実測) | esbuild で束ねればそのまま動く(実測) | asset に入れて一時フォルダへ書き出し→`dlopen`(公式ドキュメントにある手順。実測で動いた) | ✕(別の仕組みが要る) | 今のコードのまま最短で exe になる。Node 公式機能。Node 22 では `postject` で注入、Node 25 以降は `node --build-sea` で一発 |

| **Electron**(+ electron-builder) | ◎ | ◎ | インストーラ約80〜100MB / 展開後約250MB | Node がそのまま入っているので全部動く | `node-datachannel` は Electron 対応を明記。N-API なので同じ prebuild が使える(要 `asarUnpack`)。あるいは Chromium 内蔵の WebRTC を使えばネイティブアドオン自体が不要 | **◎ 標準の `Tray` API** | 重いが、トレイ・設定画面・自動更新・インストーラ・署名が全部揃っている |

### コード署名と警告(SmartScreen・Gatekeeper)

どの方法でも、**署名の無い exe/アプリは警告が出る**。ツールの選択で避けられるものではない。

- **Windows(SmartScreen)**: 署名が無いと「Windows によって PC が保護されました」が出て、
  「詳細情報 → 実行」を押してもらう必要がある。
  - 署名の選択肢は **OV証明書(年数万円〜)** か **Azure Artifact Signing(旧 Trusted Signing、
    月額数百円程度)**。ただし Azure Artifact Signing は**個人での申し込みが米国・カナダのみ**で、
    日本の個人は法人を作るか OV 証明書になる
  - **署名しても最初は警告が出る**。EV証明書による即時の信頼は 2024 年に廃止され、今は OV・
    Artifact Signing とも**ダウンロード実績が貯まるまで(数週間程度)**警告が残る
  - Microsoft Store 経由の配布なら Microsoft が署名し直すので警告は出ない(Electron は MSIX/AppX を
    出せる)。ただしストア審査の手間がある
  - SEA は `node.exe` の複製に注入するため、**元の Node の署名は壊れる**(実測で「NotSigned」に
    なった)。配るなら自前で署名し直す
- **macOS(Gatekeeper)**: Apple Developer Program(年 99 USD)で Developer ID 署名と
  **公証(notarization)**をしないと、ダウンロードした App は既定で開けない
  (macOS 15 以降は「右クリック → 開く」の抜け道も無くなり、システム設定から許可が要る)。
  SEA は `codesign --remove-signature` → 注入 → 署名し直し、が要る。Electron は
  electron-builder が署名・公証まで面倒を見る
- **当面の現実的な線**: 最初の配布は**未署名で出し、配信者ガイドに「詳細情報 → 実行」の画像付き
  手順を載せる**。利用者が増えてきたら OV 証明書(または法人化して Artifact Signing)を検討する。
  macOS は需要を見てから(VSeeFace は Windows 専用で、mac の VMC 送信アプリは少ないため優先度は低い)

## 3. タスクトレイ常駐を、どの方法なら無理なく作れるか

欲しいもの: 起動・停止、接続状態の表示(VMC を受けているか・SFU に繋がったか・席番号)、
`.env` の代わりの設定画面(配信者URLの貼り付け・ポート)、ログの確認、PC起動時の自動起動。

| 方法 | トレイ | 設定画面 | 自動起動 | 自動更新 | 評価 |
|---|---|---|---|---|---|
| **Electron** | `Tray` + `Menu` で状態ごとにアイコン・メニューを差し替え | `BrowserWindow` に HTML(既存のウィザードの画面の作りを流用できる) | `app.setLoginItemSettings()` | `electron-updater` が GitHub Releases をそのまま使う | **◎ 全部標準で揃う** |
| SEA 単体 | 作れない(Node にトレイの API が無い) | ローカルの HTTP サーバー + ブラウザで代用(ウィザードと同じ方式) | スタートアップフォルダにショートカット | 自前 | △ トレイの代わりに「黒い窓 + ブラウザの状態ページ」になる |
| Tauri + sidecar | Rust 側で作る | WebView | プラグインあり | 公式アップデータあり | ○ だが Rust と Node の2本立て |
| SEA + PowerShell の `NotifyIcon` | 一応できる | 無し | 自前 | 自前 | ✕ 壊れやすい |

**Electron が無理がない**。中継処理(`index.ts` の中身)は Electron の main プロセス(=Node)で
ほぼそのまま動き、`dgram`(UDP)も `node-datachannel` も使える。画面は既存のウィザードと同じく
素の HTML/JS で足りる。重さ(100MB 前後)は、配信者のPCが VSeeFace と配信ソフトを動かす前提の
ゲーミングPCであることを考えると許容範囲。

補足: Electron なら Chromium 内蔵の `RTCPeerConnection` を隠しウィンドウで使うこともでき、
`node-datachannel` のネイティブアドオンそのものを無くせる(`sfu.ts` はブラウザの WebRTC API と
同じ形で書かれているので移しやすい)。ただし main ⇔ renderer の受け渡しが増えるので、
**まずは `node-datachannel` を main で使い、困ったら切り替える**のがよい。

## 4. 設定を利用者に安全に渡す方法

### いまの問題: App Secret を配信者のPCに置いている

`apps/bridge/src/sfu.ts` の `SfuApi` は `CF_REALTIME_APP_SECRET` を使って
`rtc.live.cloudflare.com` を直接叩いている。運営者=配信者の今は問題にならないが、
**配信者に配る実行ファイルの設定に App Secret を入れると、それを受け取った全員が運営者の
Realtime App を自由に使える**(課金も運営者持ち)。配信者URLは管理画面でルームごとに発行・
失効できるのに、App Secret は全ルーム共通で、漏れたら作り直すしかない。

### 解決: Worker の SFU 中継 API を配信者キーで使う(Worker 側は実装済み)

HMD のブラウザ配信(`broadcast.html`)はすでに App Secret なしで配信できている。Worker
(`apps/viewer/worker/index.ts`)の次の API が配信者キー(`?key=` または `Authorization: Bearer`)
で使えるため:

| API | いまの中継プログラム | 配布版 |
|---|---|---|
| `POST /api/sfu/sessions/new` | SFU を App Secret で直接 | Worker 経由(配信者は停止中・満員の制限も対象外) |
| `POST /api/sfu/datachannels/new`(`location: 'local'`) | SFU を App Secret で直接 | Worker 経由(`local` は配信者キー必須) |
| `POST /api/sfu/publisher` | `BRIDGE_TOKEN` | 配信者キーで通る(`publisher` は配信者キーでも可) |

つまり**中継プログラムの `SfuApi` の宛先を Worker に変えるだけ**で、配信者のPCに置く秘密は
**そのルームの配信者キーだけ**になる。配信者キーは管理画面でルームを閉じれば(世代が進んで)
無効になるので、漏れても被害はそのルームに限られ、取り消せる。

ローカルの `/api/sfu/*` 中継(`index.ts` の HTTP API。App Secret をブラウザに出さないための
旧トンネル方式)と `/vrm/` 配信は、配布版では外す。

### 設定は「配信者URLを貼るだけ」にする

管理画面が出す配信者URL(`https://<Worker>/broadcast/<短縮キー>`)には、Worker の URL・
ルーム・配信者キーが全部入っている。短縮形は Worker が `broadcast.html?key=…&room=…` へ
302 で飛ばすので、中継アプリは**リダイレクト先を読めば key と room が取れる**
(`fetch(url, { redirect: 'manual' })` の `Location`)。

- 設定画面(または初回起動時のコンソール)で配信者URLを貼ってもらう
- 保存先は exe の横ではなく**利用者ごとの設定フォルダ**(Windows: `%APPDATA%\XRoomCast\`、
  macOS: `~/Library/Application Support/XRoomCast/`)。Electron なら `safeStorage`(Windows は
  DPAPI、macOS は Keychain)で配信者キーを暗号化して保存できる
- `PUBLISHER_ID` は初回にランダム生成して保存(同じPCは再起動しても同じ席に戻る)
- URL の受け渡しは今の運用どおり運営者 → 配信者へ個別に(DM 等)。**exe に設定を焼き込んで
  配ることはしない**(全員が同じバイナリを GitHub Releases から落とす形にする)
- 将来、カスタム URL スキーム(`xroomcast://…`)を登録すれば、管理画面の「中継アプリで開く」
  ボタンから設定を流し込める(Electron は `app.setAsDefaultProtocolClient()` で可能)

### 配信者ごとの区別: いまはルーム単位までしかできない

上の方式で配信者のPCに置く秘密は配信者キーだけになるが、その配信者キーは**ルームごとに1つ**で、
**配信者一人ひとりは区別できない**。`apps/viewer/worker/auth.ts` の作りは次のとおり:

| 資格情報 | 中身 | 分かること |
|---|---|---|
| 配信者キー(ルーム別) | `HMAC(ROOM_SECRET, "broadcast:<ルーム>")`(+ URLの世代) | 「このルームの配信者URLを持っている」ことだけ。同じルームの配信者は全員同じURL |
| `BROADCAST_KEY` | 全ルーム共通のマスターキー | 誰か・どのルームの人かも分からない |
| `BRIDGE_TOKEN` | 全ルーム共通のブリッジ用トークン | 同上 |
| `pid`(`PUBLISHER_ID`) | 配信元が**自分で名乗る**席の識別子。認証されない | 何も保証しない |

`authorize()` は配信者について `userId` を返さない(ログインで人を区別しているのは運営者の
管理画面の Cloudflare Access だけ)。このため、いまは次のことができない:

- **1人だけ取り消す**: ルームを閉じると、そのルームの配信者URLは全員分まとめて無効になる
- **席の乗っ取りを防ぐ**: 同じルームの別の配信者が同じ `pid` を名乗れば席を奪える。
  2人とも `PUBLISHER_ID` を設定しなければ、同じ `default` の席を取り合う
- **誰が配信したかを残す**、配信者ごとに利用量を数える・上限を設ける

「1ルーム = 1配信者」で運用している間は、ルームの区別がそのまま配信者の区別になるので実害は
小さい。複数の配信者が1つのルームを共有する(コラボ配信など)と区別できなくなる。

#### 区別できるようにする案

**案1(推奨): 配信者URLを配信者ごとに発行する**

- 管理画面で、ルームの中の配信者ごとに配信者URLを発行する。キーは
  `HMAC(ROOM_SECRET, "broadcast:<ルーム>:<世代>:<配信者ID>")` のように**配信者IDを含めて**計算し、
  URLにも配信者IDを載せる(短縮URLなら Worker が解決時に付ける)
- Worker はキーと配信者IDの組を照合し、`pid` は名乗りではなく**照合済みの配信者ID**を使う。
  これで席の乗っ取りが無くなる
- 1人だけ取り消せるように、KV に配信者ごとの世代を持たせる(ルームの世代 `room:<ルーム>` の
  `gen` と同じ仕組み。取り消すと世代が上がり、その人のURLだけが無効になる)。台帳には表示名や
  発行日時も置けるので、管理画面で「誰に渡したURLか」を一覧できる
- 照合した配信者IDを `AuthResult.userId` として返せば、Presence(Durable Object)まで届くので
  配信ログに残せる
- 中継アプリにとっても都合がよい: 配信者URLに配信者IDが入るので、**`PUBLISHER_ID` の設定が不要**
  になる(同じURLを使う限り同じ席に戻る)
- いまのルーム単位の配信者URLは、互換のため「配信者IDなし」として当面残し、管理画面で新方式の
  発行を促す。`BRIDGE_TOKEN` は配布版では使わない(配信者URLだけで動く形にするので不要)
- 規模: Worker の認可(`auth.ts`)・パブリッシャー登録・管理画面の発行と取り消し・ブラウザの
  配信者コンソールで、**2〜3日程度**

**案2: ログインで区別する**

- Cloudflare Access や独自の会員認証で配信者にログインしてもらい、`authorize()` を差し替えて
  `userId` を返す(`auth.ts` のコメントにある差し替え点)
- 厳密に区別でき、取り消しはアカウント側でできる。その代わり配信者にアカウントが要り、
  中継アプリにもログインの流れ(ブラウザでログイン → アプリにトークンを渡す)が要る
- 配信者が多くなり、会員の管理そのものが必要になってから検討すればよい

配信者に中継アプリを配る前提なら、**配信者URLがその人専用の鍵になる案1**が合っている。
§7 の段階0と一緒に入れるのが自然。

## 5. 手元での試し: SEA でビルドして起動できるか

**結果: できた。** Windows 11 / Node.js v22.23.4 で、`apps/bridge` のソースを**一切変えずに**
単一の exe にし、リポジトリ外のフォルダで起動して以下を確認した。

| 確認したこと | 結果 |
|---|---|
| exe 単体で起動する(Node 未使用・`node_modules` なし) | ○ |
| `node-datachannel` のネイティブアドオンを asset から `%TEMP%\xroomcast-bridge-<ハッシュ>\` に書き出して読み込む | ○(`RTCPeerConnection` の生成と offer 作成まで通り、その後の Cloudflare API 呼び出しがダミーの App ID で 404 になるところまで進んだ) |
| VMC(UDP)の受信(`vmcSimulator.ts` から送信) | ○ 約1900 msg/s を受信、表情辞書の登録も動いた |
| ローカル WebSocket への 30Hz 配信 | ○ 2秒で61パケット受信 |
| `/api/sfu/status` | ○ 応答あり |
| トラッキング途絶時に送信を止める | ○ |
| サイズ | exe 90.5MB、zip 圧縮で 34.6MB |
| 署名 | 元の Node の署名が壊れて `NotSigned` になる(想定どおり) |
| **実際の SFU への配信(DataChannel の open)** | ○(実装後、配信者URLで Worker 経由の配信が通り、視聴ページでアバターが動くことを実機で確かめた。2026-11-04) |

### 手順(試しに使ったもの。コミットはしていない)

1. **esbuild で1ファイルの CJS に束ねる**(esbuild はビューアの依存としてリポジトリに入っている)。
   ポイントは2つ:
   - `node-datachannel` の ESM 版は `createRequire()` 経由で `.node` を読むため、esbuild が追えない。
     esbuild のプラグインで `dist/esm/lib/node-datachannel.mjs` を差し替え、`.node` の読み込みを
     「SEA の中なら `sea.getRawAsset()` で取り出して一時フォルダに書き、`process.dlopen()`」に置き換えた
   - `import.meta.url` は CJS では空になるので、`define` で exe のパスに置き換えた
     (配布版では `.env` の読み方自体を設定フォルダ方式に変えるので不要になる)
   - `bufferutil` / `utf-8-validate`(`ws` の任意依存)は external にした
2. **SEA の設定**(`sea-config.json`): `main` に束ねた CJS、`assets` に
   `node_datachannel.node`、`disableExperimentalSEAWarning: true`
3. `node --experimental-sea-config sea-config.json` で blob を作り、`node.exe` を複製して
   `npx postject <exe> NODE_SEA_BLOB <blob> --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2`
   で注入(Node 25 以降なら `node --build-sea` で 2〜3 がまとまる)

ビルド自体は数秒。**同じ版の Node で blob を作って注入する**必要がある点と、ネイティブアドオンは
**OS・CPU ごとに別の exe** になる点(Windows x64 / macOS arm64 / macOS x64)に注意。

気づいた点:
- `osc-min` が古い `Buffer()` を使っていて、起動時に `DEP0005` の非推奨警告が出る。配布版では
  `NODE_OPTIONS` ではなくコード側で `process.noDeprecation` を立てるか、`osc-min` を置き換える
- 黒いコンソール窓が出たままになる(SEA は窓を隠せない)。段階1ではこれを「配信中の窓」として
  使い、段階2(Electron)で消す

## 6. 配布の方法

**GitHub Actions でビルドし、GitHub Releases に置く**のが一番手間が少ない。

- タグ(例: `bridge-v0.1.0`)を push したら、`windows-latest` と `macos-latest`(arm64)、
  必要なら `macos-13`(x64)で並行ビルドし、成果物をリリースに添付する
- ネイティブアドオンは `npm ci` のときに各 OS 用の prebuild が入るので、**各 OS のランナーで
  ビルドすればクロスコンパイルは要らない**
- 段階1(SEA): `xroomcast-bridge-windows-x64.zip`(exe 1つ + 短い説明 txt)を添付
- 段階2(Electron): electron-builder の `--publish always` で NSIS インストーラ(Windows)と
  dmg(macOS)を添付。`electron-updater` が同じリリースを見て自動更新する
- 署名は、証明書が手に入ったら Actions のシークレットに入れて同じワークフローで行う
  (Azure Artifact Signing なら公式の GitHub Action がある)
- ダウンロード先は配信者ガイドと、管理画面の配信者URLの横に「PC配信用の中継アプリ」として載せる

## 7. 推奨案と見積もり

### 推奨: 2段階で進める

**段階0(前提・最優先): 中継プログラムを「配信者URLだけで動く」形にする** — 約1日

1. `SfuApi` の宛先を Worker の `/api/sfu/sessions/new`・`/api/sfu/datachannels/new` に切り替え、
   認証を配信者キーにする(App Secret を使わない)
2. パブリッシャー登録・退席も配信者キーで行う(`BRIDGE_TOKEN` は後方互換で残してもよい)
3. 設定の入口を「配信者URL」1つにし、リダイレクト先から Worker の URL・ルーム・キーを取り出す
4. 設定の置き場を `%APPDATA%\XRoomCast\config.json`(macOS は Application Support)に。
   リポジトリの `.env` は開発用として引き続き読めるようにする
5. ローカル `/api/sfu/*` 中継と `/vrm/` 配信を、配布版では無効にする(開発用のフラグで残す)
6. 実際の Worker に対して、本物の配信者URLで SFU 配信が通ることを確認する
7. セットアップウィザード・配信者ガイド・SETUP.md の説明を合わせる

これだけで、今の `配信開始.bat` 運用でも App Secret を配信者に渡さずに済む。

続けて(または同時に)、**配信者URLを配信者ごとに発行する**(§4 の案1)— 約2〜3日。
中継アプリの設定から `PUBLISHER_ID` が消え、1人だけの取り消しと席の乗っ取り防止ができる。
配布を始める前に入れておくと、配った後でURLの形式を変えずに済む。

**段階1: SEA で「ダブルクリックで動く exe」** — 約2〜3日

1. §5 のビルド手順を `apps/bridge/scripts/build-sea.mjs` として整え、`npm run build:exe` にする
2. 初回起動時に配信者URLを聞いて保存する(コンソールでの入力。2回目以降はそのまま起動)
3. 状態表示を配信者向けの日本語に整える(「VSeeFace からの受信: OK」「配信: 接続済み(席 0)」等)
4. GitHub Actions(Windows のみで開始)でタグから Releases へ
5. 配信者ガイドに、ダウンロード・SmartScreen の「詳細情報 → 実行」・URL の貼り付けを画像付きで書く

**段階2: Electron のトレイ常駐アプリ** — 約1〜2週間

1. `apps/bridge-app`(Electron)を作り、中継処理を main プロセスで動かす
   (段階0〜1で `index.ts` を「起動・停止できるモジュール」に切り出しておくと楽)
2. トレイ: 状態(停止中 / 待機中 / VMC受信中 / 配信中 / エラー)ごとのアイコンとメニュー
   (開始・停止・設定・ログ・視聴ページを開く・終了)
3. 設定画面: 配信者URLの貼り付けと検証、ポート、PC起動時に自動起動、`safeStorage` での保存
4. electron-builder で NSIS インストーラ + `electron-updater` の自動更新
5. macOS 版(dmg)。署名・公証は Apple Developer Program に入るかどうかを決めてから
6. 段階1の exe は、軽量版・トラブル時の予備として残すか、廃止するかを決める

### 段階2を Electron にする理由(Tauri・Bun ではなく)

- リポジトリが TypeScript だけで書かれており、中継処理をそのまま載せられる(Tauri は Rust が増える)
- トレイ・設定画面・自動起動・自動更新・インストーラ・署名・公証が標準で揃う
- `node-datachannel` が Electron 対応を明記しており、駄目なら Chromium 内蔵の WebRTC に逃げられる
- 欠点はサイズ(100MB 前後)だが、配信者のPCの前提(VSeeFace が動くPC)なら問題になりにくい
